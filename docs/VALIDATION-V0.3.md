# v0.3 验证记录

本次在保留 DSH 适配器、固定 bridge/sync 依赖与 v2 映射的前提下增加安全运行能力，没有接入 deepseek-as-subagent。以下区分代码验证与真实目标验收，不能沿用 v0.2 的模型成功结果证明新能力已经在真机启用。

## 自动验证覆盖

新增测试覆盖固定只读能力、工具定义替换、源码祖先/子目录冲突、只读共享、Windows 大小写与根边界、跨进程竞争、持久锁重载、错误所有者释放、状态损坏、扫描超限、凭据/符号链接排除、文件新增修改删除、结束后目录删除，以及完成审计前不解锁。

Hub 和 companion 模拟集成覆盖：不支持的目标拒绝只读、旧普通派工兼容、锁或基线失败不发提示、模式与恢复冻结、超时和取消仍保留活动运行、切换默认目标不改投、审计失败保留后端完成证据，以及真实工作区归属与独立 cwd 在新流程中继续正确。

本机 Windows / Node 24.14.1 的最终结果：`npm test` **141/141 通过**；`npm run check` 通过，0 错误、0 告警；CLI 帮助显示 v0.3.0，包含 `dispatch-readonly` 与 `changes`。配套包 `npm pack --ignore-scripts` 成功，包含运行时、源码锁、快照和安全运行模块。CI 的 Windows/Ubuntu、Node 22 结果以对应提交为准，不把本机测试等同于其他平台验收。

## 已选定真实实例

只使用用户明确指定的公司 Windows 本机 DSH rc.3；没有连接家用或其他远程实例。通过真实 owner API 核对实例与当前 companion 能力；旧 companion 不宣告安全运行时，v0.3 控制端及 stdio MCP 的 `hub_dispatch_readonly` 真实返回 `readonly-unsupported`，回执没有 session ID 和 request ID，未创建模型任务。这验证了升级前不会静默降级成提示词只读。

DSH 当前配置模型为 `deepseek-flash / high`。实现调查和成套委派实际返回 `402 / ACCOUNT_QUOTA`；一个任务尝试申请 Windows ACL 修复权限，操作没有获批且该任务已取消，没有修改 ACL。主会话没有切换模型、放宽全局权限或改用其他子代理。

本机已安装的 companion 仍为 v0.2。DSH 公开插件管理器在 HMR 运行时拒绝更新已安装包（`already-installed`），本仓库安装器也要求退出桌面后再更新；本次不强行停止程序或改写运行中的插件文件。因此新版目标端工具 guard、租约和快照的**真实 DSH 模型端到端验收尚未通过**，不能宣称已在当前桌面启用。

## 补验条件与剩余限制

在模型额度可用、现有任务结束并由用户正常退出 DSH 后，按 [安装交接](../README-AI.md) 更新所选 companion，保持原实例身份和模型。重启后先核对 `safeRunsVersion:1`、工作区与目录映射，再创建一次性测试映射和独立任务：只读任务能阅读而写入被拒绝；重叠写任务被阻止；完成后 `changes` 中的哈希与实际产物相符。不要在正式源码中做破坏性写入测试。

远程实例、其他 DSH 版本、PTC preset 的不同组合只具有模拟或源码合同验证，没有真实端点验收。租约不协调旧/非 Hub 会话、IDE、其他实例或脱离会话的 Shell 后台任务；记录只覆盖有界且未排除的声明写目录，不是逐次修改日志、内容备份或完整归因证据。准备事务异常中断或未见终止证据的运行保守持锁，不自动按时间/PID 回收，接手方式见 [安全执行说明](README-SAFETY.md)。
