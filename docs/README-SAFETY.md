# 只读调查、源码并发与文件记录

多个执行任务访问同一份源码时，只靠任务书约定容易同时改文件；等待超时也不能说明模型已经停止。v0.3 在现有 DSH 接入上增加工具能力、目标端源码租约和文件元数据记录。没有引入其他模型执行框架，也不改变 DSH 当前模型、登录或全局权限。

## 只读任务怎样发起

使用独立入口，不能把普通派工中的“先不要修改”当成强制只读：

```sh
node bin/adh.mjs dispatch-readonly --target <target> --workspace <mapping> --text "调查测试入口，说明风险和依据。"
node bin/adh.mjs changes --job <job-id>
```

MCP 使用 `hub_dispatch_readonly`，参数与 `hub_dispatch` 相同。会话能力写入回执和 DSH 目标端记录，后续 `send` 仍然只读。需要改代码时新建普通派工任务，不能通过提示词升级原会话。

目标端使用 DSH 公开工具注册服务的执行 guard，允许已经核对的原生 `read`、`glob`、`grep` 定义；写入、编辑、Shell、`run_code`、MCP、子代理及配置工具均拒绝。工具定义被替换后也拒绝，不能仅凭同名工具绕过限制。继承工具另加可见性限制，原生工具展示不可用时在发送提示前报错。

这是模型工具的只读能力，不禁止 DSH 自己写会话日志或搜索结果溢出文件。读写目录范围仍是任务指令和 DSH 原有权限共同处理，不能将只读能力、界面分组或源码租约解释成任意目录的 OS 沙箱。插件必须保持加载，不能防止宿主管理员禁用插件或其他插件直接操作文件。

MCP 参数文件可参考 [只读任务示例](../examples/readonly-task.example.json)，替换其中目标和映射占位值后，运行 `node scripts/call-tool.mjs hub_dispatch_readonly <参数文件>`。

## 同一源码怎样并发

新版 companion 宣告 `safeRunsVersion: 1` 后，**新任务**在每次提示发送前申请租约。源码目录与声明的写目录按目标机真实路径核对；祖先与子目录视为重叠，Windows 大小写按目标规则处理。不同目标别名指向同一 DSH 实例时也共享锁表。

| 同一实例中目录重叠的任务 | 结果 |
| --- | --- |
| 只读与只读 | 可以共享 |
| 写任务与只读 | 后来的任务报 `source-locked`，不发送提示 |
| 写任务与写任务 | 后来的任务报 `source-locked`，不发送提示 |
| 目录不重叠 | 可以并行 |

每个新安全任务同一时间只允许一个请求，不能在前一个请求仍持锁时排入下一个修改。独立任务 cwd 不等于独立源码；希望并行实现时，应由用户明确准备不同源码副本或 Git worktree，再配置映射。

锁保存在目标 DSH profile 的私有状态中。控制端退出、超时、取消请求和默认目标切换均不直接释放。`wait` 或 `changes` 会核对原请求的唯一用户事件、后续终止事件、实际 Agent 及其原生子代理的活动和空 inbox；再完成快照，才释放租约。子代理身份持久记录，重启后也检查其日志与队列，不靠临时父子关系漏放锁。取消保留排队工作时继续持锁。已完成记录可以重复查询，不重新执行模型任务。

这些租约只协调同一 DSH 实例中新版 Hub 管理的任务，不协调旧会话、其他实例、IDE、人工操作和 Shell 启动后脱离会话的后台程序。文件记录反映时间区间内看到的变化，不保证归因给某个模型。

## 文件记录覆盖什么

普通写任务在发送提示前和确认结束后扫描**声明的写目录**，记录相对路径、类型、大小、权限模式及 SHA-256，返回 `added`、`modified`、`deleted`。记录不保存正文，不自动恢复文件，也不是每次修改前的持久化日志。

默认上限为 2500 个文件、单文件 2 MiB、总内容 32 MiB、20 秒。忽略版本库、依赖、构建和缓存目录、常见凭据文件及符号链接，并报告排除规则与数量；不读取链接目标。只读任务不做文件快照，回执明确标为 `changeCapture: not-captured-readonly`，空列表不能用于证明外部参与者没有改文件。

扫描超限、文件不稳定、不可读或目录被替换时明确失败，不返回“完整”的部分记录。结束后根目录被删除可以记录删除；审计先于 cwd 的结束核验，所以产物和完成证据不会因 cwd 漂移被覆盖。失败时继续持锁，修复扫描问题后重试 `changes`。Node 的路径式文件 API 无法对抗所有恶意文件系统替换，Windows 尤其不能提供原子的目录句柄遍历；这不是防恶意宿主的文件安全边界。

较大项目可由目标端管理员在 companion 的 profile patch 配置 `snapshotLimits`，支持 `maxFiles`、`maxFileBytes`、`maxTotalBytes`、`maxMillis`；未设置项保留默认值，未知字段和无效值拒绝。`target inspect` 返回生效上限。每次运行从基线冻结这些值，执行中更改配置不会放宽原请求的结束扫描。不要为了扫描通过删除业务文件，也不要自动扩大上限。

## 升级和异常接手

配置仍使用 v2，无需把路径或实例重写为新格式。更新 Hub 后，按 [AI 安装交接](../README-AI.md) 更新所选 profile 的 companion；需要退出 DSH 时先等现有任务结束，由用户正常退出，安装器不强杀进程。远程管理员在对应目标上更新同一个配套包，不把本机状态目录复制到远程。

先 `target inspect <target>` 核对实例与 `capabilities.safeRunsVersion`。旧 companion 允许普通派工，但回执显示 `safety.supported: false`，不声称已经加锁或记录；只读派工直接拒绝。旧任务没有 `safetyVersion`，不自动补加限制、扫描、锁或移动会话。

出现 `run-admission-unconfirmed` 时没有发送模型提示，但目标可能已保存租约或基线。保留原 job/request ID，查看 `receipt`，不要自动新建同一修改任务或删除锁文件。`prompt-admission-uncertain` 则可能已经发送；`retry` 只确认原请求，不重发。当前版本不自动清理中断的准备事务、遗留短事务锁或未进入终止事件的运行；需要管理员核对目标记录、原请求和实际活动后处理。不能只凭时间或控制端 PID 判断锁失效。

`hub_changes` / `changes` 使用回执的原目标，支持指定历史 `requestId`。它会写审计并可能释放已结束租约，因此 MCP 不标记为只读操作。配套协议细节见 [实现契约](SAFETY-V0.3.md)，本次验证范围见 [验证记录](VALIDATION-V0.3.md)。
