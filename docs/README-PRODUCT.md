# 产品与使用方式

Agent Dispatch Hub 解决的是规划者与执行环境之间的交接。GPT 可以继续负责需求澄清、拆分工作和审查结果，把具体任务交给 DSH 中可用的模型执行；hub 负责把任务送到明确选择的环境，并保留后续追问、等待、查看消息和取消所需的任务回执。

## 哪些工作适合这样协作

当你希望一个 AI 统筹项目，同时让已有 DSH 环境完成代码调查、实现或验证时，可以为每个环境配置 target，再把允许使用的项目目录映射为工作区别名。目标可分别命名为 `office`、`home`，工作区可命名为 `demo`；这些名字不决定机器位置，实际连接与路径由配置决定。

每次执行前，规划者应把需求、允许修改范围和验收条件写清楚。执行完成后，规划者结合模型消息和真实产物审查结果。模型声称完成并不自动代表文件正确或业务验收通过。

工作目录只是 DSH 执行命令的起点，不会自动成为源码副本或隔离的 Git 工作树。任务书应分别说明工作目录、实际源码目录、可读写范围和验收条件；并行任务还要避免同时写同一文件。

## 一次任务怎样流转

1. 查看目标和状态，明确选择目标及其工作区。
2. 使用 `dispatch` 或 `hub_dispatch` 发送任务，保存返回的 job ID。
3. 使用该 job ID 等待、查看消息或追加指令。
4. 核对实际产物，再决定继续执行还是结束任务。

```sh
node bin/adh.mjs dispatch --target office --workspace demo --text "请调查当前项目的测试入口，只输出结论，先不要修改文件。"
node bin/adh.mjs wait --job <返回的job-id>
node bin/adh.mjs messages --job <返回的job-id>
node bin/adh.mjs send --job <返回的job-id> --text "请补充相关文件位置与核对依据。"
node bin/adh.mjs cancel --job <返回的job-id>
```

后续操作始终沿用回执中的目标。把默认目标从 `office` 改为 `home` 不会迁移已有任务；修改原目标的连接会使旧回执失效，直到恢复原连接，避免将同一 session ID 发送给另一套 DSH。

## v0.2.0 的边界

每个映射分别保存原生 DSH 工作区、独立任务目录规则、源码目录和范围。缺失归属或目录时拒绝，不落入“未分组”。[配置与迁移](README-PLACEMENT.md) 说明新旧配置如何衔接。任务范围是显式指令约定；DSH 原生分组不构成文件权限隔离。

当前只提供 DSH 后端、本机与远程目标路由、CLI、MCP、任务回执和主动验收入口。它没有把 DSH 模型变成 Codex 原生子代理，也不让 Codex 的模型密钥自动用于其他平台。模型选择、账户登录、可用额度及执行权限由 DSH 一侧负责。

本机安装会接入 `dsh-codex-sync`，同步所选本机 profile 的技能和 MCP 配置，并排除 Hub 自身以避免回环。切换到远程 target 只改变派工位置，不会自动把本机源码、技能、MCP 凭据或模型密钥上传到远程；远程项目和能力需由该环境准备。

远程连接要求 HTTPS 和有效凭据；hub 不会自动接管桌面应用、猜测远程路径或绕过图形登录。任务会使用所选模型及工作区的实际权限，配置前应确认它们符合任务需要。

后续可以增加其他执行后端。新适配器接入通用的状态、派发、消息、等待和取消接口；是否支持某个后端，以具体版本的已实现适配器为准。
